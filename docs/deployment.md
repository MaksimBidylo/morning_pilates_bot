# Релизы и развёртывание

[README](../README.md) · [Пользовательские пути](user-flows.md) · [Архитектура](architecture.md) · [Разработка](development.md)

Цепочка выпуска: **проверенный коммит → Git-тег → публикация
GitHub Release → Deploy to Render**.

## Теги и версии

После push в `main` [CI](../.github/workflows/ci.yaml) запускает сборку, тесты,
ktlint и detekt. После успешного CI отдельный [Tag](../.github/workflows/tag.yaml)
берёт SHA именно проверенного main-коммита и вызывает [tag.py](../.github/scripts/tag.py).
Повторной сборки в Tag нет. Для PR тег не создаётся.

### Правила версий

Первый тег, если релизных тегов ещё нет, — `v0.1.0`. Далее скрипт анализирует
коммиты после предыдущего тега:

| Изменение | Повышение |
|---|---|
| `feat:` / `feat(scope):` | minor |
| `!` перед двоеточием или footer `BREAKING CHANGE:` / `BREAKING-CHANGE:` | major |
| Остальное, включая `fix`, `docs`, `test`, `chore` | patch |

При нескольких типах выбирается наибольшее повышение. Повтор уже тегированного
коммита не создаёт новый тег; если более новый коммит уже получил тег, старый
не тегируется. Тег аннотированный, отдельная ветка не создаётся.
Версия приложения в Gradle — `0.1.0-SNAPSHOT`; версию выпуска определяет Git-тег.

Документационный merge также может получить patch-тег. Создание тега
само по себе не создаёт GitHub Release и не вызывает Deploy.

## Настройка окружения Render

Используется Web Service с Docker-образом из [Dockerfile](../Dockerfile).
Сборка выполняет `installDist` на JDK 25, runtime — JRE 25 с пользователем `10001`.
Тесты выполняются в CI, а не при сборке образа. Локальные Compose, `.env`
и `application-local.conf` в этот запуск не входят.

Настройте сервис на репозиторий, ветку `main` и Dockerfile `./Dockerfile`.
Отключите автоматический деплой каждого push и используйте workflow выпуска.

Ktor слушает `0.0.0.0`; порт берётся из `PORT`, по умолчанию `8080`.
HTTP healthcheck — `/health`. Он не проверяет Telegram и БД.

### Переменные приложения

| Переменная | Значение |
|---|---|
| `TRAINING_TIME_PICKER_ENABLED` | Независимый выбор времени `/training_add`; по умолчанию `false`, изменение требует перезапуска |
| `TRAINING_SEARCH_DATE_CALENDAR_ENABLED` | Независимый временный флаг календаря `/training_get_date`; по умолчанию `false`, изменение требует перезапуска |
| `TRAINING_DATE_CALENDAR_ENABLED` | Временный флаг календаря даты `/training_add`; по умолчанию `false`, включение — `true`, изменение требует перезапуска |
| `TELEGRAM_BOT_TOKEN` | Токен именно этого окружения |
| `TELEGRAM_ID_ENCRYPTION_KEY` | Base64 от 32 случайных байт |
| `TELEGRAM_ID_LOOKUP_KEY` | Другой независимый Base64-ключ той же длины |
| `DB_HOST`, `DB_PORT` | Адрес и порт доступной сервису PostgreSQL |
| `DB_DATABASE`, `DB_USER`, `DB_PASSWORD` | База и учётные данные окружения |
| `DB_SSL_MODE` | SSL-режим подключения; задайте согласно требованиям БД, например `require` |
| `DB_POOL_SIZE` | Размер пула; по умолчанию `5`, согласуйте с лимитом БД |
| `LOG_LEVEL` | При необходимости; по умолчанию `INFO` |
| `TELEGRAM_LOG_LEVEL` | Диагностика Telegram; по умолчанию `INFO`, независимо от общего уровня |

Источник — [application.conf](../src/main/resources/application.conf).
При Render Postgres используйте параметры подключения своей БД и подходящий
для сервиса внутренний адрес. Не переносите локальный пароль `morning_pilates`
в production.

Два ключа создаются отдельно на доверенном компьютере:

```sh
openssl rand -base64 32
openssl rand -base64 32
```

Значения должны различаться и после Base64-декодирования иметь по 32 байта.
Сохраните их в секретах окружения и защищённой резервной копии, а не в Git,
Dockerfile, build arguments, скриншотах или логах. Не генерируйте ключи при каждом
деплое. Для восстановления данных нужны **БД и исходные ключи**.
Автоматическая ротация ключей не реализована; резервное копирование настраивается отдельно.

Flyway выполняется при старте до polling. При ошибке миграции запуск прерывается.
Не удаляйте таблицы и не исправляйте checksum применённой миграции вручную:
сначала установите причину ошибки.

### Secrets GitHub Actions

[Deploy](../.github/workflows/deploy.yaml) использует:

| Secret | Назначение |
|---|---|
| `RENDER_DEPLOY_HOOK_URL` | Вызов деплоя нужного Web Service; URL сам является секретом |
| `RENDER_API_KEY` | Чтение истории и статуса деплоя через Render API |

ID сервиса извлекается из hook URL. Секреты приложения, включая токен бота
и ключи Telegram ID, задаются в окружении самого сервиса.
`SONAR_TOKEN` относится к анализу кода, не к деплою.

## Публикация и ручной деплой

1. Влейте принятые изменения в `main`, дождитесь успешного CI и тега для нужного SHA.
2. Проверьте настройки Render и secrets. Выберите существующий тег
   при подготовке GitHub Release, укажите возможности и ограничения версии.
3. Опубликуйте Release. Событие `release: published` запускает деплой,
   в том числе для pre-release, в тот же настроенный сервис Render.
4. Дождитесь результата Deploy и проверьте фактический SHA в Render, затем выполните
   краткую проверку приложения ниже.

Сохранение черновика и редактирование Release не запускают деплой.
Для повторного деплоя или отката есть ручной запуск:
**Actions → Deploy to Render → Run workflow**, ветка `main`, параметр `tag`.
Workflow допускает только `vMAJOR.MINOR.PATCH`, без суффикса в имени тега;
ручной запуск с другой ветки запрещён самим workflow.

Для старого тега, не содержащего обработчик события публикации Release,
используйте ручной workflow из main. В текущем Deploy checkout скриптов выполняется
из main; выбранный тег определяет SHA **приложения**, передаваемый в Render.

## Что проверяет Deploy

Workflow разрешает тег в SHA, проверяет принадлежность истории main и наличие
успешного CI для push этого коммита. Затем
[deploy_render.py](../.github/scripts/deploy_render.py) проверяет доступ Render API,
запоминает прежние deploy ID и вызывает hook с `ref=<полный SHA>`.

Ответ hook о запуске или очереди не считается завершённым деплоем. Скрипт ждёт
`live` именно нового деплоя выбранного SHA. Статус опрашивается с интервалом
15 секунд; лимит job — 10 минут. Ошибки сборки/старта, отмена, неизвестный статус,
таймаут или неоднозначность нового деплоя завершают проверку ошибкой.

POST запуска деплоя не повторяется автоматически. Временные ошибки чтения статуса
могут повторяться в пределах ожидания. При таймауте деплой может продолжаться
в Render: сначала проверьте историю, затем решайте, нужен ли новый запуск.

Summary содержит результат отслеживания, SHA и ссылку на сервис, когда выполнение
дошло до его записи. При раннем отказе API/hook или прерывании job Summary может
отсутствовать; используйте лог. Скрипт маскирует секреты в обработанных HTTP-ошибках,
но не публикуйте необработанный вывод с конфигурацией окружения.

## Приёмка выпуска MVP

Зафиксируйте тег, SHA, окружение, имя бота и дату проверки.

| Проверка | Ожидание |
|---|---|
| Deploy | В Render работает выбранный SHA, а не только получен ответ hook |
| HTTP | `/health` возвращает `200` и `OK` |
| Telegram | `/start` отвечает; команды дневника работают в личном чате |
| Профиль | У тестового пользователя без тренировок `/profile` открывается; поле сохраняется, меняется и очищается; завершение возвращает карточку с кнопкой «Редактировать» |
| Календарь (если включён) | В `/training_add` показывается текущий месяц; выбор дня переводит ко времени, ручная дата также работает. При `false` остаётся прежний текстовый вопрос |
| Запись | Специальная тестовая тренировка сохраняется и читается новым запросом |
| Просмотр | Последняя и поиск по дате показывают нужные записи, навигация не размножает сообщения |
| Удаление | Отмена сохраняет запись; подтверждение удаляет только выбранную; новый поиск подтверждает результат |
| Сохранность после рестарта | В тестовом окружении сохраните поле профиля и тренировку, начните редактирование и перезапустите приложение с той же БД и ключами. Новые `/profile` и команды просмотра показывают сохранённые данные; незавершённый ввод не восстанавливается |
| Восстановление | `/cancel` и `/cancel_all` позволяют завершить тестовое действие и начать новое |

Полные [пользовательские пути](user-flows.md) служат основой расширенного прогона.
Ошибки БД, подмену callback и отказ Telegram проверяют автоматические тесты;
не ломайте рабочее окружение ради ручной приёмки.

## Перезапуски, откат и ограничения

Используйте один активный процесс бота на токен;
не запускайте одновременно локальную и удалённую копии с одним токеном.
Черновики тренировок, просмотр дневника и экран профиля с незавершённым вводом
находятся в памяти и сбрасываются при перезапуске. Сохранённые тренировки и поля
профиля остаются в PostgreSQL и читаются новыми командами. Старые кнопки не продолжают
действия прежнего процесса. Горизонтальное масштабирование с разделяемыми сессиями
не реализовано.

При откате выберите предыдущий проверенный тег через ручной Deploy и заранее
проверьте совместимость кода со схемой БД. Возврат версии приложения не выполняет
обратную миграцию и не восстанавливает удалённые пользовательские записи.
Сохраните прежние ключи защиты ID; их замена не является способом отката.

`live` подтверждает успешный деплой, но не заменяет мониторинг сервиса.
`/health` не является сквозной проверкой Telegram/БД. Резервное копирование,
проверка восстановления и алерты настраиваются отдельно.

## Проверка скриптов

Без обращения к рабочим API GitHub/Render:

```sh
python3 -m unittest discover -s .github/scripts/tests
```

Compose-тестам из этого набора нужен установленный Docker Compose CLI.
Подробности локальных проверок — в [development.md](development.md#тесты-и-анализаторы).

Календари создания и поиска оставляйте выключенными для пользователей до завершения
#149, #150, #151, #153 и общей ручной приёмки. В тестовом окружении проверьте
поиск через календарь и текст, возврат «Выбрать другую дату», отмену, восстановление
удалённого сообщения и прежний текстовый поиск при выключенном флаге.

Выбор времени также оставляйте выключенным до общей приёмки. В тестовом окружении
проверьте часы → минуты, «Назад», ручное время с произвольной минутой, ошибку ввода
с предупреждением над клавиатурой, повторный `/training_add` и отмену. Отдельно
проверьте прежний текстовый шаг с `TRAINING_TIME_PICKER_ENABLED=false`.

## Диагностика Telegram в Render

В Render откройте сервис → **Logs**, выберите время инцидента и ищите
`event=telegram_received` / `event=telegram_completed`. Скопируйте
`correlation_id` из записи и отфильтруйте по нему все строки одного обращения.
Logback пишет в stdout, время — UTC, длительность — монотонные миллисекунды.
Никаких дополнительных сервисов сбора логов не требуется.

Уровни задаются в **Environment** с последующим перезапуском сервиса:

- `LOG_LEVEL=INFO` — общий уровень приложения.
- `TELEGRAM_LOG_LEVEL=INFO` — отдельный уровень диагностики Telegram (по умолчанию).
  `WARN` оставит неизвестные результаты и технические ошибки; `ERROR` — только
  технические ошибки. Для расследования сохраняйте `INFO`, чтобы видеть начало
  и завершение. `DEBUG` не добавляет содержимое событий.

`kind` принимает `command`, `text`, `callback`, `other`. `route` — только имя из
списка известных команд или пространство callback (`training`, `profile`, `view`,
`training_calendar`, `training_time`, `date_search`); нераспознанное значение —
`unknown`. Аргументы команды и callback payload не выводятся. UUID корреляции
создаётся заново для каждого прохождения update и не связан с Telegram ID.

| `result` | Значение | Уровень завершения |
|---|---|---|
| `success` | Есть явный сигнал принятого бизнес-результата, технических ошибок не зафиксировано | INFO |
| `rejected` | Ожидаемый отказ/невалидный ввод, технических ошибок не зафиксировано | INFO |
| `technical_failure` | Исключение, неуспешный/нечитаемый ответ Telegram API либо ошибка БД, включая `Result.failure` | ERROR |
| `unknown` | Сценарий не сообщил достоверный результат; отсутствие исключения не доказывает успех | WARN |

Пример одного обезличенного обращения (префикс времени/потока опущен):

```text
event=telegram_received correlation_id=7508c071-a1fe-4c51-a079-976b52b115f1 kind=text route=unknown
event=telegram_completed correlation_id=7508c071-a1fe-4c51-a079-976b52b115f1 kind=text route=unknown result=rejected duration_ms=12
```

Ошибка БД в другом обращении:

```text
event=telegram_failure correlation_id=939e7d5c-d54f-45b1-b70d-a6636776cfe5 kind=command route=training_get_last http_status=none sql_state=08006
java.lang.RuntimeException: org.jooq.exception.DataAccessException
    ... стек и обезличенные типы причин ...
event=telegram_completed correlation_id=939e7d5c-d54f-45b1-b70d-a6636776cfe5 kind=command route=training_get_last result=technical_failure duration_ms=10015
```

Первая техническая ошибка обращения получает отдельную диагностическую запись:
тип исключения, стек и типы причин (до восьми уровней), проверенный SQLSTATE,
HTTP-статус при наличии. Исходные сообщения исключений, SQL, причины с текстом,
подавленные сообщения и response body не печатаются. Следующие ошибки того же
update сохраняют итог `technical_failure`, но не добавляют повторные стеки.
Даже при успешном повторе/восстановлении после ошибки Telegram API итог остаётся
консервативным `technical_failure`; это не утверждение об откате бизнес-операции.

SDK работает через **long polling**, не через HTTP webhook. Отдельная запись
`event=telegram_polling_failure result=technical_failure` означает сбой получения
updates: конкретное событие ещё не поступило, поэтому correlation ID отсутствует.
SDK передаёт в этот hook только небезопасное текстовое описание; оно опускается.
Проверяйте также наличие последующих `telegram_received`. Для `/health` не включён
дополнительный access log, чтобы проверки Render не создавали шум. `/health`
подтверждает работу HTTP-сервера, но не исправность polling или PostgreSQL.

Логи SDK отключены через `LogLevel.None`, включая прямой `printStackTrace` и
OkHttp HTTP logging. В Logback отключены SQL/HTTP/пул/миграционные логгеры jOOQ,
PostgreSQL, Hikari, Flyway, OkHttp, Retrofit и SDK даже при общем `DEBUG`.
PostgreSQL JUL дополнительно отключается перед созданием пула. Не включайте их
в production: запросы, параметры, URL с токеном и исключения могут раскрывать
данные. Вместо этого используйте обезличенную диагностику приложения.
