# Релизы и развёртывание

[README](../README.md) · [Пользовательские пути](user-flows.md) · [Архитектура](architecture.md) · [Разработка](development.md)

В репозитории предусмотрена цепочка **проверенный коммит → Git-тег → публикация
GitHub Release → Deploy to Render**. Наличие этой конфигурации не подтверждает
фактические настройки аккаунта Render, secrets, опубликованный релиз или текущую
версию работающего сервиса. Их проверяют при выпуске.

## Теги и версии

После push в `main` [CI](../.github/workflows/ci.yaml) запускает сборку, тесты,
ktlint и detekt. После успешного CI отдельный [Tag](../.github/workflows/tag.yaml)
берёт SHA именно проверенного main-коммита и вызывает [tag.py](../.github/scripts/tag.py).
Повторной сборки в Tag нет. Для PR тег не создаётся.

### Правила версий

Первый тег, если релизных тегов ещё нет, — `v0.1.0`. Далее скрипт анализирует
коммиты после предыдущего тега:

| Изменение | Повышение |
|---|---|
| `feat:` / `feat(scope):` | minor |
| `!` перед двоеточием или footer `BREAKING CHANGE:` / `BREAKING-CHANGE:` | major |
| Остальное, включая `fix`, `docs`, `test`, `chore` | patch |

При нескольких типах выбирается наибольшее повышение. Повтор уже тегированного
коммита не создаёт новый тег; опоздавший CI старого коммита не должен выпускать
его поверх более нового. Тег аннотированный, отдельная ветка не создаётся.
Версия приложения в Gradle пока `0.1.0-SNAPSHOT`; не путайте её с релизным тегом.

**Даже документационный merge может получить новый patch-тег.** Создание тега
само по себе не создаёт GitHub Release и не вызывает Deploy. Номер MVP не следует
назначать в README вручную: выбирайте существующий тег проверенной версии.

## Настройка окружения Render

Используется Web Service с Docker-образом из [Dockerfile](../Dockerfile).
Сборка выполняет `installDist` на JDK 25, runtime — JRE 25 с пользователем `10001`.
Docker-сборка не является полным тестовым прогоном. Локальные Compose, `.env`
и `application-local.conf` в этот запуск не входят.

Для управляемого выпуска настройте сервис на репозиторий, ветку `main`, Dockerfile
`./Dockerfile`, отключите автоматический деплой каждого push и используйте
описанный ниже workflow. Это требуемая настройка, не утверждение, что она уже
включена в панели конкретного сервиса.

Ktor слушает `0.0.0.0`; порт берётся из `PORT`, по умолчанию `8080`.
HTTP healthcheck — `/health`. Он не проверяет Telegram и БД.

### Переменные приложения

| Переменная | Значение |
|---|---|
| `TELEGRAM_BOT_TOKEN` | Токен именно этого окружения |
| `TELEGRAM_ID_ENCRYPTION_KEY` | Base64 от 32 случайных байт |
| `TELEGRAM_ID_LOOKUP_KEY` | Другой независимый Base64-ключ той же длины |
| `DB_HOST`, `DB_PORT` | Адрес и порт доступной сервису PostgreSQL |
| `DB_DATABASE`, `DB_USER`, `DB_PASSWORD` | База и учётные данные окружения |
| `DB_SSL_MODE` | SSL-режим подключения; задайте согласно требованиям БД, например `require` |
| `DB_POOL_SIZE` | Размер пула; по умолчанию `5`, согласуйте с лимитом БД |
| `LOG_LEVEL` | При необходимости; по умолчанию `INFO` |

Источник — [application.conf](../src/main/resources/application.conf).
При Render Postgres используйте параметры подключения своей БД и подходящий
для сервиса внутренний адрес. Не переносите локальный пароль `morning_pilates`
в production. Параметры тарифа, доступность БД и сетевые правила проверяются
в конкретном окружении; репозиторий их не настраивает.

Два ключа создаются отдельно на доверенном компьютере:

```sh
openssl rand -base64 32
openssl rand -base64 32
```

Значения должны различаться и после Base64-декодирования иметь по 32 байта.
Сохраните их в секретах окружения и защищённой резервной копии, а не в Git,
Dockerfile, build arguments, скриншотах или логах. Не генерируйте ключи при каждом
деплое. Для восстановления данных нужны **БД и исходные ключи**; автоматическая
ротация и резервное копирование этой инструкцией не настраиваются.

Flyway выполняется при старте до polling. Ошибка миграции — причина неуспешного
старта, а не основание удалять таблицы или вручную править checksum старой миграции.

### Secrets GitHub Actions

[Deploy](../.github/workflows/deploy.yaml) использует:

| Secret | Назначение |
|---|---|
| `RENDER_DEPLOY_HOOK_URL` | Вызов деплоя нужного Web Service; URL сам является секретом |
| `RENDER_API_KEY` | Чтение истории и статуса деплоя через Render API |

ID сервиса извлекается из hook URL. Секреты приложения, включая токен бота
и ключи Telegram ID, должны быть заданы в окружении самого сервиса; эти два
GitHub secret их не заменяют. `SONAR_TOKEN` относится к анализу кода, не к деплою.

## Публикация и ручной деплой

1. Влейте принятые изменения в `main`, дождитесь успешного CI и тега для нужного SHA.
   Не подставляйте текущую вершину main вместо проверенного коммита.
2. Проверьте наличие настроек Render и secrets. Выберите уже существующий тег
   при подготовке GitHub Release, укажите возможности, ограничения и проверенную версию.
3. Опубликуйте Release. Workflow подписан на `release: published`; у него нет
   фильтра, исключающего pre-release. Публикацию pre-release не считайте изолированным
   тестовым деплоем: он использует тот же настроенный сервис.
4. Дождитесь результата Deploy и проверьте фактический SHA в Render, затем выполните
   краткую проверку приложения ниже.

Сохранение черновика и редактирование Release не являются событием `published`.
Для повторного деплоя или отката есть ручной запуск:
**Actions → Deploy to Render → Run workflow**, ветка `main`, параметр `tag`.
Workflow допускает только `vMAJOR.MINOR.PATCH`, без суффикса в имени тега;
ручной запуск с другой ветки запрещён самим workflow.

Для старого тега, не содержащего обработчик события публикации Release,
используйте ручной workflow из main. В текущем Deploy checkout скриптов выполняется
из main; выбранный тег определяет SHA **приложения**, передаваемый в Render.

## Что проверяет Deploy

Workflow разрешает тег в SHA, проверяет принадлежность истории main и наличие
успешного CI для push этого коммита. Затем
[deploy_render.py](../.github/scripts/deploy_render.py) проверяет доступ Render API,
запоминает прежние deploy ID и вызывает hook с `ref=<полный SHA>`.

Ответ hook о запуске или очереди не считается завершённым деплоем. Скрипт ждёт
`live` именно нового деплоя выбранного SHA. Статус опрашивается с интервалом
15 секунд; лимит job — 10 минут. Ошибки сборки/старта, отмена, неизвестный статус,
таймаут или неоднозначность нового деплоя завершают проверку ошибкой.

POST запуска деплоя не повторяется автоматически. Временные ошибки чтения статуса
могут повторяться в пределах ожидания. При таймауте деплой может продолжаться
в Render: сначала проверьте историю, затем решайте, нужен ли новый запуск.

Summary содержит результат отслеживания, SHA и ссылку на сервис, когда выполнение
дошло до его записи. При раннем отказе API/hook или прерывании job Summary может
отсутствовать; используйте лог. Скрипт маскирует секреты в обработанных HTTP-ошибках,
но не публикуйте необработанный вывод с конфигурацией окружения.

## Приёмка выпуска MVP

Это последовательность действий для выпуска, а не автоматически установленный PASS.
Зафиксируйте тег, SHA, окружение, имя бота и дату проверки.

| Проверка | Ожидание |
|---|---|
| Deploy | В Render работает выбранный SHA, а не только получен ответ hook |
| HTTP | `/health` возвращает `200` и `OK` |
| Telegram | `/start` отвечает; команды дневника работают в личном чате |
| Запись | Специальная тестовая тренировка сохраняется и читается новым запросом |
| Просмотр | Последняя и поиск по дате показывают нужные записи, навигация не размножает сообщения |
| Удаление | Отмена сохраняет запись; подтверждение удаляет только выбранную; новый поиск подтверждает результат |
| Восстановление | `/cancel` и `/cancel_all` позволяют завершить тестовое действие и начать новое |

Полные [пользовательские пути](user-flows.md) служат основой расширенного прогона.
Ошибки БД, подмену callback и отказ Telegram проверяют автоматические тесты;
не ломайте рабочее окружение ради ручной приёмки. Число тестов и результат
последнего запуска нужно брать из его отчёта, не из статического текста документа.

После подтверждения готовности можно публиковать MVP первым пользователям.
Документационный PR сам по себе не создаёт Release, не меняет секреты и не
выполняет новый деплой. Проверка исходников не доказывает, какой SHA был развёрнут
во время ранее проведённого ручного теста.

## Перезапуски, откат и ограничения

Для текущей архитектуры используйте один активный процесс бота на токен;
не запускайте одновременно локальную и удалённую копии с одним токеном.
Создание и просмотр находятся в памяти, поэтому перезапуск сбрасывает их.
Сохранённые тренировки остаются в PostgreSQL. Не обещайте пользователям сохранность
незавершённого ввода при выкладке. Горизонтальное масштабирование с разделяемыми
сессиями не реализовано.

При откате выберите предыдущий проверенный тег через ручной Deploy и заранее
проверьте совместимость кода со схемой БД. Возврат версии приложения не выполняет
обратную миграцию и не восстанавливает удалённые пользовательские записи.
Сохраните прежние ключи защиты ID; их замена не является способом отката.

`live` подтверждает состояние конкретного деплоя в момент проверки, не непрерывную
доступность сервиса. `/health` не является сквозным мониторингом Telegram/БД.
Автоматические резервные копии, алерты, гарантии доступности тарифа и проверенное
восстановление нужно настраивать и подтверждать отдельно — они не следуют из
наличия workflow.

## Проверка скриптов

Без обращения к рабочим API GitHub/Render:

```sh
python3 -m unittest discover -s .github/scripts/tests
```

Compose-тестам из этого набора нужен установленный Docker Compose CLI.
Подробности локальных проверок — в [development.md](development.md#тесты-и-анализаторы).
